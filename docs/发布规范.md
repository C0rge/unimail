# 发布与版本规范

这份文档记录本仓库的版本号来源、tag 约定与发布流程。目的很具体：**把「看起来像遗漏、其实是刻意为之」的状态写清楚**，避免下次有人（包括我自己）把它当成 bug 去"修"。

## 1. 版本号的单一事实源

`unimail/config.py` 里的 `APP_VERSION` 是**唯一**的版本号定义处。以下全部从它派生，不存在第二份需要同步的副本：

| 使用处 | 派生方式 |
|---|---|
| `unimail.__version__` | `unimail/__init__.py` 里 `from .config import APP_VERSION` |
| 关于对话框标题 | `ui/dialogs.py` 直接读常量 |
| 163 适配器的 IMAP `ID` 命令 | `platforms/adapters.py` 插值常量 |
| 打包后的包元数据 | `pyproject.toml` 的 `[tool.setuptools.dynamic] version = { attr = "unimail.config.APP_VERSION" }` |

因此**发版时只需要改一处**：`APP_VERSION`。改完同步 `CHANGELOG.md` 增补小节即可。

依赖同理：`[project].dependencies` 通过 `dynamic` 直读 `requirements.txt`，不在 `pyproject.toml` 里重抄一遍。开发依赖**刻意不在 `pyproject.toml` 声明** —— `requirements-dev.txt` 用了 `-r requirements.txt` 这种标准包含写法，而 setuptools 的 `{ file = [...] }` 不支持 `-r` 展开，想声明 extras 就只能把依赖再抄一份，正好制造漂移。开发环境按 README 走 `pip install -r requirements-dev.txt`。

## 2. tag 命名与类型

- 格式：`vX.Y.Z`（语义化版本，见 `CHANGELOG.md` 顶部）。
- **约定：使用附注 tag（annotated tag）**，消息格式见下一节。
- 校验方式：`git cat-file -t <tag>` 返回 `tag` 为附注、返回 `commit` 为轻量。

### 已知例外：`v1.6.0` 是轻量 tag

`v1.6.0` → `git cat-file -t` 返回 `commit`，与 `v1.0.0` / `v1.1.0` / `v1.2.0` / `v1.3.0` 都不同。

**这是刻意保持的，不是遗漏。** 该 tag 已经挂着 GitHub Release 与 53 MB 的 exe 资产，改成附注 tag 必须 force-push 一个已经被他人 fetch 过的 tag 对象：所有克隆过的人都会看到 tag 冲突，而收益只是元数据形式统一。风险大于收益，故保留原状。**从 `v1.6.1` 起恢复使用附注 tag**——`v1.6.0` 是仓库里唯一一个刻意保留的轻量 tag，此后新增的 tag 一律附注。

## 3. tag 消息格式

与 `v1.1.0` / `v1.2.0` / `v1.3.0` 保持一致：

```text
UniMail vX.Y.Z — <一句话主题>

<2~4 行：修了哪些严重问题、加了什么能力。优先写「不修会怎样」，
因为这类缺陷通常不报错、只安静地破坏数据。>

DB vA -> vB（幂等迁移）。        # 无数据库迁移时省略此行
```

## 4. 有版本号却没有 tag / Release 的情况

两种情况性质不同，**都不是"忘了发"**：

| 版本 | tag | Release | 说明 |
|---|---|---|---|
| `v1.4.0` | 无 | 无 | **有意**：`CHANGELOG` 已声明 1.4.0 / 1.5.0 / 1.6.0 三个阶段在本批次一并完成并交付，仓库只发布 v1.6.0 一个版本，三个小节按阶段拆分记录各自改动范围 |
| `v1.5.0` | 无 | 无 | 同上 |
| `v1.2.0` | **有**（事后补建） | 无 | tag 指向 `e15ec00`（提交信息里写明 `(v1.2.0)`），与其它版本的 tag 风格一致。此前只有 `CHANGELOG` 的 `[1.2.0]` 小节而无 tag、无 Release，读者按 changelog 找下载会落空，故补齐 tag。**没有 Release 同样是刻意的**：该版本未产出可执行文件资产，而 Release 只给真正提供 exe 下载的版本 |
| `v1.6.2` | 待建 | 待建 | **有意暂缓**：`APP_VERSION` 与 `CHANGELOG` / `RELEASE_NOTES` / `使用说明` 已一并改到 1.6.2（这三处必须同步，`pack_release.py` 对「说明标题含 `APP_VERSION`」是硬校验），但尚未执行 `build_exe.py` 与 `pack_release.py`。**发版时按 §6 清单从第 5 步接着做即可**，不要以为漏了第 1–4 步 |

当前发布状态（截至 `v1.6.1`）：

- tag：`v1.0.0` / `v1.1.0` / `v1.2.0` / `v1.3.0` / `v1.6.0` / `v1.6.1`
- Release：`v1.0.0` / `v1.1.0` / `v1.3.0` / `v1.6.0` / `v1.6.1`，每个都带一个 Windows 资产
- tag 类型分布：`v1.6.0` 是**唯一**一个轻量 tag（原因见 §2），`v1.6.1` 起全部为附注 tag

## 5. Release 资产约定

- 文件名：`UniMail-vX.Y.Z-Windows-x64.zip`
- 内容：`UniMail.exe` + `使用说明.md` + `README.md` + `CHANGELOG.md` + `LICENSE`
  （zip 内**平铺**，不带顶层目录）
- 构建：
  ```bash
  python build_exe.py            # PyInstaller，默认 onefile → dist/UniMail.exe
  python tools/pack_release.py   # → dist/release/UniMail-vX.Y.Z-Windows-x64.zip
  ```
- **`使用说明.md` 是仓库根目录下受版本控制的文件**，不是打包时手写的。
  此前它完全不在仓库里（只在某个 zip 里存在过），后果是 v1.1.0 的发布包中
  装着的仍是 v1.0.0 的说明，且没有任何机制能发现。`pack_release.py` 会把
  「说明的标题必须含当前 `APP_VERSION`」作为硬校验，不一致直接失败。
- 体积参考：v1.0.0 48.7 MB → v1.6.0 53.0 MB → v1.6.1 55.1 MB
  （v1.6.1 起发布包内置 SQLCipher 驱动，比不带驱动时大约 2.3 MB；不带驱动的
  发布包会静默运行在字段级加密下，见 §6 检查清单的构建前校验）

## 6. 发版检查清单

1. 改 `unimail/config.py` 的 `APP_VERSION`（**只此一处**）
2. 在 `CHANGELOG.md` 顶部增补 `## [X.Y.Z] - YYYY-MM-DD` 小节
3. 更新 `RELEASE_NOTES.md`（它是最新版的 Release 正文）
4. 跑测试，两种环境各一遍（装 / 未装 `sqlcipher3`，断言数差 3 项属正常）：
   ```bash
   python tests/smoke.py
   ```
5. 打包并组装 zip（`python tools/pack_release.py` 会校验版本号与随包文件齐全）：
   ```bash
   python build_exe.py
   python tools/pack_release.py
   ```
6. 建**附注 tag**（`git tag -a`），消息按 §3 格式
7. 推送 `main` 与 tag
8. 建 GitHub Release，上传 zip 作为资产
9. 以匿名身份验证下载链接可达（`curl -sIL` 应得 `200`，且内容以 `PK` 开头）
10. 确认 `.git/config` 无令牌残留（推送若用过带令牌的 URL，记得还原）
